## 2. The Canonical Terminology System

### 2.1 Governing Glossary

**FACT:** The canonical glossary (`standards/csl/shared/reference/glossary/GLOSSARY.md`, 246 lines) defines the following terms normatively:

| Term | Definition (summary) |
|---|---|
| Abstract Syntax Tree (AST) | Structured representation of parsed CSL source prior to semantic interpretation |
| Approval | Governance decision authorizing an engineering action; shall be explicit and auditable |
| Artifact | Derived engineering output generated from the UEM; not Canonical Knowledge |
| Audit | Permanent historical record of engineering actions; immutable |
| Canonical Knowledge | Authoritative engineering knowledge in CSL; single source of engineering truth |
| Compiler | System that transforms Canonical Knowledge into UEM and Engineering Artifacts |
| Constraint | Rule limiting or validating engineering knowledge; violations prevent validation |
| Dependency | Relationship expressing that one artifact requires another |
| Document | Fundamental unit of canonical engineering knowledge |
| Engine | An execution component that processes canonical knowledge |
| Entity | A modeled engineering concept with properties and relationships |
| Governance | The control system over engineering knowledge and processes |
| Identifier | Unique canonical name for an engineering object |
| Knowledge | Engineering information expressed in CSL form |
| Lifecycle | The defined sequence of states through which an artifact transitions |
| Namespace | Organizational scope containing canonical identifiers |
| Policy | Governance rule controlling engineering behavior |
| Relationship | Formal directed edge connecting two canonical entities |
| Rule | Deterministic engineering logic; machine-validatable |
| Semantic Model | Meaning layer of CSL; independent of syntax |
| Universal Engineering Model | Graph of semantic entities generated by compilation |
| Validator | System that checks canonical documents for compliance |
| Version | A declared revision state of an artifact |

**ENGINEERING CONCLUSION:** The canonical terminology system is coherent and well-designed. Each term has a specific engineering meaning that distinguishes it from its everyday meaning. Particularly important: "Knowledge" ≠ "Document", "Artifact" ≠ "Canonical Knowledge", "Rule" ≠ "Policy" ≠ "Constraint". These distinctions are load-bearing in the semantic model.

### 2.2 The Knowledge/Artifact Distinction

**FACT:** The glossary states: "Artifacts are derived engineering outputs generated from the Universal Engineering Model. Artifacts are not Canonical Knowledge."

**ENGINEERING CONCLUSION:** This is the most fundamental terminological distinction in the Canonical System: **canonical knowledge** is the source, **artifacts** are the derivatives. Source code, documentation, tests, and deployment descriptors are all artifacts. They are never canonical knowledge. This distinction is the philosophical cornerstone of the "single source of truth" principle.

### 2.3 Terminology Gaps

**ENGINEERING CONCLUSION:** The glossary defines terms for the current v1 system but does not cover several concepts introduced by v2's file structure:

- **Engineering Alphabet** (CSL-001) — not in glossary
- **Reasoning Model** (CSL-007) — not in glossary  
- **Module** (CSL-016) — not in glossary
- **Package** (CSL-015) — not in glossary
- **Extension** — appears in v1 language spec but not in glossary

These are terminology gaps that must be resolved when CSL v2 is authored.

**ENGINEERING CONCLUSION:** The keyword system is extensive and covers: containment hierarchy (Project → Capability → Feature → Requirement), governance concepts (Policy, Rule, Constraint, Risk), lifecycle concepts (State, Transition, Event), relational concepts (Dependency, Reference, Interface), and measurement (Goal, Metric, Test). This is a semantically rich vocabulary for engineering knowledge.

Goals track desired outcomes measured by Metrics. This is a complete, internally consistent domain model for software engineering knowledge.

## 4. The Grammar Architecture

### 4.1 Four-Layer Grammar Model

**FACT:** CSL v1 Volume IV defines a four-layer grammar:

```
Layer 1: Lexical Grammar
  Input:  Raw text
  Output: Token stream
  Rules:  Character classes, reserved words, literals, whitespace handling

Layer 2: Syntactic Grammar
  Input:  Token stream
  Output: Parse tree
  Rules:  Statement structure, block composition, expression grammar

Layer 3: Structural Grammar
  Input:  Parse tree
  Output: Structural representation
  Rules:  Mandatory sections, identifier uniqueness, composition rules

Layer 4: Semantic Validation
  Input:  Structural representation
  Output: Validated semantic representation / validation errors
  Rules:  Type constraints, relationship validity, consistency rules
```

**ENGINEERING CONCLUSION:** This four-layer grammar is a clean, well-designed language architecture. It strictly separates: tokenization (Layer 1) → syntax (Layer 2) → structure (Layer 3) → semantics (Layer 4). Many language specifications blur these layers; CSL v1 kept them distinct, which is architecturally correct and enables independent testing of each layer.

### 4.2 Grammar Formalism

**ENGINEERING CONCLUSION:** The v1 grammar is specified in prose, not in a formal grammar notation (BNF, EBNF, PEG, or similar). This is a significant specification limitation: prose grammar rules are ambiguous and cannot be mechanically verified for completeness or consistency.

**ENGINEERING HYPOTHESIS:** The absence of a formal BNF/EBNF grammar in v1 was a conscious or practical decision — formal grammar notations require more authoring effort and technical expertise. The consequence is that the prose grammar, while clear in intent, cannot be mechanically converted to a parser generator input without interpretation decisions.

### 4.3 Grammar Objectives

**FACT:** Volume IV states that the grammar shall be: "Deterministic. Human Readable. Machine Readable. Predictable. Consistent. Extensible. Versioned." and "shall minimize ambiguity."

**ENGINEERING CONCLUSION:** These objectives are well-chosen but "minimize ambiguity" is weaker than "eliminate ambiguity." A formal grammar would eliminate ambiguity by construction; a prose grammar can only minimize it. This suggests that CSL v2's grammar specification (CSL-002) should be written in formal grammar notation to achieve true determinism.

### 4.4 Token Types

**FACT:** Volume IV defines token categories: Identifier, Keyword, Literal, Number, String, Boolean, Reference, Operator, Delimiter, Comment, Whitespace.

**ENGINEERING CONCLUSION:** These token categories are standard for a specification language. The presence of `Reference` as a distinct token type is interesting — it suggests that cross-document references have special lexical status and are not just identifiers. This is architecturally important: the lexer must be able to distinguish a local identifier from a reference to another canonical document.

## 5. The Semantic Categories

### 5.1 Core Semantic Categories

**FACT:** CSL v1 Volume III defines the Core Semantic Categories as:

- **Knowledge** — the fundamental information carrier
- **Entity** — a modeled engineering concept
- **Relationship** — a directed edge between entities
- **Constraint** — a validation rule applied to the knowledge graph
- **Policy** — a governance rule applied to the knowledge graph
- **Rule** — deterministic logic applied to the knowledge graph
- **Artifact** — a derived output from the knowledge graph
- **Action** — an executable step in an engineering lifecycle

**ENGINEERING CONCLUSION:** These eight semantic categories are the core type system of CSL. Every keyword maps to one of these categories. For example: Requirement is a Knowledge, Component is an Entity, Dependency is a Relationship, Constraint is a Constraint, Policy is a Policy, Rule is a Rule, Test is an Artifact, Action is an Action.

### 5.2 Semantic Equivalence

**FACT:** Volume III states: "Multiple syntactic representations may describe identical semantics. Equivalent semantics shall produce equivalent Universal Engineering Models."

**ENGINEERING CONCLUSION:** Semantic equivalence is a normative requirement. This means that if two authors write the same requirement in different syntactic forms, the compiler must produce identical UEM output. This is the CSL version of "there is no meaningful distinction between semantically equivalent representations" — a strong requirement that places the burden of normalization on the compiler, not the author.

### 5.3 The Type System

**FACT:** Volume III defines a type hierarchy for semantic objects.

**FACT:** The shared type system (`standards/csl/shared/ontology/TYPE_SYSTEM.md`) is empty.

**ENGINEERING CONCLUSION:** The type system is defined in prose in Volume III but was never formalized as a machine-readable schema. This means there is no canonical reference that a compiler can use to validate type correctness algorithmically. The type system exists as engineering intent but not as engineering artifact.

## 6. The Normative Language System

### 6.1 CSS-003 Normative Vocabulary

**FACT:** CSS-003 (Normative Language, 323 lines) defines requirement levels following RFC 2119 conventions:

| Term | Level | Meaning |
|---|---|---|
| SHALL / MUST | Mandatory | Requirement is obligatory; non-compliance is a violation |
| SHALL NOT / MUST NOT | Prohibited | Compliance forbids this behavior |
| SHOULD | Recommended | Strongly recommended; deviation requires justification |
| SHOULD NOT | Discouraged | Strongly discouraged; adoption requires justification |
| MAY | Optional | Permitted but not required |

**ENGINEERING CONCLUSION:** CSS-003 adopts the RFC 2119 vocabulary, which is a well-established standard for normative specification language. This choice is sound: it gives all canonical specifications a shared, unambiguous vocabulary for expressing requirement strength.

### 6.2 Normative Language Consistency Observation

**ENGINEERING CONCLUSION:** The CSL v1 volumes use SHALL/MUST but do not consistently follow CSS-003 conventions — they were authored before CSS was defined. CSS-003 was a later addition that formalized what the v1 volumes did informally. This creates a retroactive compliance issue: CSL v1 volumes are normative but were not written to CSS-003 standards.

**EVIDENCE:** CSL v1 Volume I uses both "shall" and "must" in lowercase without consistent normative convention. CSS-003 requires uppercase for normative terms.

## 7. The Relationship Model

### 7.1 Canonical Relationship Types

**FACT:** The relationship reference (`standards/csl/shared/reference/relationships/RELATIONSHIP_REFERENCE.md`) defines canonical relationship types.

**ENGINEERING CONCLUSION:** The relationship model distinguishes between:

- **Dependency relationships** — A requires B to function
- **Traceability relationships** — A traces to B (requirement satisfaction)
- **Composition relationships** — A contains B
- **Inheritance relationships** — A is-a B
- **Reference relationships** — A cites B
- **Temporal relationships** — A precedes B in lifecycle

**ENGINEERING CONCLUSION:** These relationship types form the edge vocabulary of the Universal Engineering Model's knowledge graph. Without a formally specified relationship type system, the UEM cannot be validated for relational consistency.

### 7.2 CDM-016 Relationship Model

**FACT:** CDM-016 (Document Relationship Model) is a placeholder.

**ENGINEERING CONCLUSION:** The document-level relationship model — which would define what kinds of formal relationships can exist between CDM documents — has not been specified. This means that while CSL defines knowledge-level relationships, the corresponding document-level relationship model is absent. This gap makes it impossible to validate cross-document relationships formally.
