## 1. Purpose

This document describes the complete intended architecture of the Canonical Foundation — the abstraction layers, the dependency chain, and the structural organization of CSL, CDM, and CSS as engineering components.

---

## 2. The Three-Tier Canonical Foundation

### 2.1 The Top-Level Architecture

**FACT:** The dependency order established across CSS, CDM, and CSL documents is:

```
CSS  — Canonical Standards System
 ↓     (governs how specifications are written)
CDM  — Canonical Document Model
 ↓     (governs what documents are as engineering objects)
CSL  — Canonical Specification Language
 ↓     (governs how canonical knowledge is expressed)
Canonical Standards
 ↓
Engineering Engines
 ↓
Platforms
```

**ENGINEERING CONCLUSION:** This is a strict downward dependency chain. CSS knows nothing about CDM. CDM depends on CSS (every CDM document must conform to CSS). CSL depends on CDM (every CSL document is a CDM document). Canonical Standards depend on CSL (they are expressed in CSL). Engineering Engines consume Canonical Standards. Platforms are deployed by Engines.

### 2.2 The Layering Rationale

**ENGINEERING CONCLUSION:** The three-tier canonical foundation represents three distinct governance domains:

| Tier | Domain | Governs |
|---|---|---|
| CSS | Authoring Governance | How specifications are written as human-readable artifacts |
| CDM | Document Object Governance | What a document is as a managed engineering object |
| CSL | Knowledge Governance | How engineering knowledge is expressed in machine-readable form |

These are genuinely distinct concerns. A document can satisfy CSS (well-authored) and CDM (well-identified) but contain poorly expressed CSL knowledge. Conversely, the same CSL knowledge can be expressed in documents that violate CSS authoring rules. The separation is architecturally sound.

## 3. The CSL Five-Layer Engineering Model

### 3.1 Layer Definitions

**FACT:** CSL v1 Volume I (Foundations) defines five engineering layers:

```
Layer 1: Human Vision
  - Purpose, Mission, Values, Constraints
  - Authored by humans in natural language
  - Does not enter CSL directly

Layer 2: Canonical Knowledge
  - Requirements, Policies, Rules, Concepts, Decisions
  - Expressed in CSL
  - Single source of truth

Layer 3: Universal Engineering Model
  - Semantic Entities, Relationships, Constraints, Dependency Graph
  - Generated by compilation from Layer 2
  - Technology-independent intermediate representation

Layer 4: Engineering Artifacts
  - Documentation, Architecture, Roadmaps, Source Code, Tests, Deployment
  - Generated from Layer 3
  - Technology-specific outputs

Layer 5: Execution Environment
  - Runtime, Platform, Infrastructure
  - Deployed from Layer 4
  - Beyond the scope of CSL's direct governance
```

### 3.2 Layer Boundary Analysis

**ENGINEERING CONCLUSION:** The most important boundary is between Layer 2 and Layer 3. This is the compilation boundary: human-authored canonical knowledge (Layer 2) is compiled into the Universal Engineering Model (Layer 3). Everything below this boundary is derivable; everything above it is authoritative.

**ENGINEERING CONCLUSION:** The second important boundary is between Layer 1 and Layer 2. Layer 1 (human vision) does not enter CSL directly — it is the human context from which CSL knowledge is derived. This boundary acknowledges that not all engineering knowledge is formalizable — purpose and values remain human artifacts.

**ENGINEERING CONCLUSION:** Layer 4 is intentionally plural: multiple different artifact types are generated from the same Layer 3 model. This is why the compilation model specifies: documentation artifacts, architecture artifacts, code structure artifacts, test artifacts, deployment artifacts, AI prompt artifacts. They all come from the same UEM, but they are projected in different directions.

## 4. The CDM Architecture

### 4.1 CDM's Internal Architecture

**FACT:** CDM Architecture document (`standards/cdm/architecture/CDM_ARCHITECTURE.md`) defines CDM as having the following internal components:

```
CDM-000: Document Model        — the root specification
    ├── CDM-001: Metadata Model    — document metadata and attributes
    ├── CDM-002: Identifier Model  — document identity and naming
    ├── CDM-003: Lifecycle         — document state machine
    ├── CDM-004: Dependencies      — dependency graph
    ├── CDM-005: Traceability      — knowledge traceability
    ├── CDM-006: Versioning        — version management
    ├── CDM-007: Governance        — change control
    ├── CDM-008: Validation Model  — validation rules
    ├── CDM-009: Executable Docs   — executable document model
    ├── CDM-010: Canonical Header  — header format definition
    ├── CDM-011: Document Graph    — relationship graph model
    ├── CDM-012: Query Language    — document query language
    ├── CDM-013: Index             — document indexing
    ├── CDM-014: Namespace         — namespace scoping
    ├── CDM-015: Schema            — document schema
    ├── CDM-016: Relationship Model— relationship types
    ├── CDM-017: Classification    — document taxonomy
    ├── CDM-018: Security Model    — access and security
    └── CDM-019: Reference Impl   — reference implementation
```

**ENGINEERING CONCLUSION:** CDM was designed as a comprehensive document engineering system with 20 child specifications. The three implemented specifications (CDM-000 through CDM-002) form the core identity model. The 17 unimplemented specifications form the lifecycle, graph, query, governance, and security layers.

### 4.2 CDM Dependency Tiers

**ENGINEERING CONCLUSION:** The CDM internal architecture has four dependency tiers:

**Tier 1 — Identity Foundation (implemented):**
- CDM-000 (Document Model) — the root
- CDM-001 (Metadata Model) — attributes
- CDM-002 (Identifier Model) — identity

**Tier 2 — Lifecycle and Governance (unimplemented, required for validator):**
- CDM-003 (Lifecycle) — state machine
- CDM-007 (Governance) — change control
- CDM-008 (Validation Model) — validation rules
- CDM-010 (Canonical Header) — header definition

**Tier 3 — Relational Model (unimplemented, required for graph):**
- CDM-004 (Dependencies)
- CDM-005 (Traceability)
- CDM-006 (Versioning)
- CDM-011 (Document Graph)
- CDM-016 (Relationship Model)
- CDM-017 (Classification)

**Tier 4 — Advanced Capabilities (unimplemented, future):**
- CDM-009 (Executable Documents)
- CDM-012 (Query Language)
- CDM-013 (Index)
- CDM-014 (Namespace)
- CDM-015 (Schema)
- CDM-018 (Security Model)
- CDM-019 (Reference Implementation)

## 5. The CSS Architecture

### 5.1 CSS Internal Structure

**FACT:** CSS covers six core specifications (all implemented) plus architecture and meta documents:

```
CSS-000: Specification Model     — what a canonical specification is
CSS-001: Standard Authoring Guide— how to write canonical specifications
CSS-002: Document Style Guide    — how to format canonical specifications
CSS-003: Normative Language      — the vocabulary of canonical requirements
CSS-004: Specification Checklist — the validation checklist for specifications
CSS-005: Reference Specification — a worked example
```

**ENGINEERING CONCLUSION:** CSS is designed as an authoring system. CSS-000 defines the concept. CSS-001 through CSS-004 define the rules. CSS-005 demonstrates compliance. This is a pedagogically complete set: concept → rules → demonstration.

### 5.2 CSS's Relationship to Other Standards

**ENGINEERING CONCLUSION:** CSS operates as a meta-constraint on all other canonical standards. The relationship is:

- Every CDM document must satisfy CSS-001, CSS-003, and CSS-004
- Every CSL document must satisfy CSS-001, CSS-003, and CSS-004
- Every CANON document must satisfy CSS-001, CSS-003, and CSS-004
- CSS documents themselves must satisfy CSS

This universal applicability makes CSS the most powerful architectural constraint in the Canonical Foundation.

## 6. The CSL Architecture

### 6.1 CSL v1 Internal Architecture

**FACT:** CSL v1 is organized as eight sequential volumes with deliberate architectural intent:

```
Vol I:   Foundations           — conceptual and philosophical foundation
Vol II:  Language Specification— syntax and language constructs
Vol III: Semantic Model        — meaning and type system
Vol IV:  Grammar               — formal grammar (four layers)
Vol V:   Compiler Specification— compilation pipeline
Vol VI:  Universal Engineering Model — the output model
Vol VII: Safety and Governance — safety constraints and governance
Vol VIII:Reference Implementation — implementation reference
```

**ENGINEERING CONCLUSION:** The v1 architecture follows a deliberate progression from abstract to concrete: philosophy → language → meaning → grammar → compiler → output model → safety → implementation. This is a complete language specification lifecycle.

### 6.2 CSL v2 Intended Architecture

**FACT:** The CSL v2 file structure declares 31 core specifications (CSL-000 through CSL-030) plus 16 governance and process documents.

**ENGINEERING CONCLUSION:** The v2 architecture is significantly larger than v1. It expands the language with:

**Core Language Tier (CSL-000 to CSL-007):**
- CSL-000: Language Manifest
- CSL-001: Engineering Alphabet
- CSL-002: Grammar
- CSL-003: Semantic Type System
- CSL-004: Object Model
- CSL-005: Relationship Model
- CSL-006: Knowledge Representation
- CSL-007: Reasoning Model

**Tooling Tier (CSL-008 to CSL-016):**
- CSL-008: Runtime Specification
- CSL-009: Language Evolution
- CSL-010: Compiler Specification
- CSL-011: Validator Specification
- CSL-012: Parser Specification
- CSL-013: Lexer Specification
- CSL-014: AST Specification
- CSL-015: Package Format
- CSL-016: Module System

**Ecosystem Tier (CSL-017 to CSL-025):**
- CSL-017: Standard Library
- CSL-018: Extension Framework
- CSL-019: Interoperability
- CSL-020: Conformance Test Suite
- CSL-021: Error Model
- CSL-022: Diagnostics
- CSL-023: Serialization
- CSL-024: Binary Format
- CSL-025: Query Language

**Runtime Tier (CSL-026 to CSL-030):**
- CSL-026: Execution Model
- CSL-027: Security Model
- CSL-028: Performance Model
- CSL-029: Reference Implementation Guide
- CSL-030: Ecosystem Specification

**ENGINEERING CONCLUSION:** CSL v2 adds three tiers that v1 did not have: explicit tooling specifications (lexer, AST, parser, validator), ecosystem specifications (module system, extension framework, standard library), and a runtime tier (execution model, security model). This is the architectural distance between v1 (a specification language) and v2 (a full language platform).

### 7.2 The Blocking Dependency Chain

**ENGINEERING CONCLUSION:** The blocking dependency chain for completing the Canonical Foundation is:

1. CSS is complete → can begin CSS validator immediately
2. CDM-001 and CDM-002 are complete → can begin CDM header validator immediately
3. CSL v1 grammar is complete → can validate v1 CSL documents
4. **CSL-002 (v2 Grammar) is empty** → v2 parser cannot begin
5. CDM Tier 2 is empty → full document lifecycle cannot be validated
6. Shared ontology is empty → machine-readable semantic model does not exist

The entire v2 language platform is blocked on CSL-002.
